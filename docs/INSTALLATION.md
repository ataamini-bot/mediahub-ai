# نصب و نگهداری MediaHub AI نسخهٔ ۱

این بسته نامزد `v1.0.0-rc.1` است. تگ پایدار پس از تست نصب تازه و پذیرش مالک
منتشر می‌شود. موفقیت CI جای تست زندهٔ Telegram و پایلوت را نمی‌گیرد.

## شروع

Ubuntu Server 22.04، 24.04 یا 26.04 با معماری amd64 و دسترسی sudo لازم است.
Docker Engine/Compose و ابزارهای میزبان در نصاب نصب می‌شوند. سرویس‌های Backend،
Bot، Worker، Monitor، Backup، PostgreSQL، Redis، Local Bot API و سرویس کمکی یوتیوب
داخل Docker هستند. سرویس `bgutil-provider` فقط در شبکهٔ داخلی Docker در دسترس است.

پس از انتشار تگ و موفقیت ساخت Imageهای همان نسخه:

```bash
version='v1.0.0'
curl -fL --proto '=https' "https://raw.githubusercontent.com/ataamini-bot/mediahub-ai/${version}/install.sh" -o /tmp/mediahub-install.sh
sudo bash /tmp/mediahub-install.sh "$version"
```

تا انتشار تگ این نمونه آمادهٔ اجرا نیست. برای نامزد آزمایشی از SHA کاملِ دارای
CI موفق استفاده می‌شود. نامزد بدون تگ Imageها را روی سرور می‌سازد؛ تگ رسمی آنها
را از GHCR دریافت می‌کند، revision را با commit تطبیق می‌دهد و digest را ثبت می‌کند.
مسیر پیش‌فرض `/opt/mediahub-ai` است. پوشهٔ موجود بازنویسی نمی‌شود.
از checkout موجود نیز `sudo bash scripts/install.sh` منوی راه‌اندازی را باز می‌کند.

## منوی `sudo mediahub`

متن‌های منو، پرسش‌ها و خطاهای نصاب انگلیسی‌اند تا در ترمینال‌های بدون پشتیبانی
نمایش راست‌به‌چپ خوانا باشند. زبان رابط ربات از داخل خود ربات انتخاب می‌شود.

| گزینه | کارکرد |
|---|---|
| Install MediaHub | اطلاعات تلگرام، تولید کلیدها، migration، سرویس‌ها، بکاپ و تست بازیابی |
| Update to a stable release | نسخهٔ مشخص، بکاپ پیش از migration و بازگشت برنامه هنگام شکست |
| Create and export backup | آرشیو رمزنگاری‌شده و checksum، تست بازیابی و خروجی به پوشه انتخابی |
| Import backup and restore | همین سرور یا Ubuntu جدید با کلید مستقل |
| Telegram group, topics, and required channels | اتصال گروه مالک، ساخت تاپیک و کانال عضویت بر اساس زبان |
| Check system health | وضعیت سرویس‌ها، دیتابیس، بکاپ و پاک‌سازی فایل‌ها |
| Roll back application | Imageهای قبلی؛ دیتابیس خودکار downgrade نمی‌شود |
| Configure update source | مخزن HTTPS و رجیستری قابل اعتماد |
| Uninstall containers (keep data) | حذف کانتینرها پس از بکاپ با حفظ volumeها و فایل‌های پشتیبان |

## ورودی‌های نصب

1. Bot Token از `@BotFather`؛ ورودی مخفی است.
2. Telegram API ID و API Hash از `https://my.telegram.org/apps` برای Local Bot API.
3. Telegram ID عددی مثبت اولین سوپرادمین.
4. منطقهٔ زمانی؛ پیش‌فرض `Asia/Tehran`.

رمز PostgreSQL، کلید API داخلی و کلیدهای رمزنگاری خودکار ساخته می‌شوند. `.env`
مجوز 600 دارد. ادامهٔ نصب ناتمام کلیدهای قبلی را عوض نمی‌کند. نصب موجود از مسیر
Update نگهداری می‌شود. ساخت ربات در BotFather و دریافت API ID/Hash را مالک انجام می‌دهد.
شماره تلفن، OTP و ورود حساب شخصی تلگرام در این روش لازم نیست.

کلید `DATA_ENCRYPTION_KEY` را جدا و امن خارج از سرور نگه دارید. برای نصب تازه،
نسخهٔ محلی در `/opt/mediahub-ai/.mediahub/recovery-key.txt` با مجوز 600 ذخیره می‌شود.
کلید داخل آرشیو رمزنگاری‌شده به‌تنهایی برای بازکردن همان آرشیو کافی نیست.

## گروه و تاپیک‌ها

طبق تصمیم مالک در ۱ اکتبر ۲۰۲۶، ادمین سوپرگروه را می‌سازد و نصاب تاپیک‌ها را ایجاد می‌کند:

1. گروه خصوصی مانند `MediaHub AI Monitor` بسازید و Topics را فعال کنید.
2. ربات را به گروه اضافه و با دسترسی Manage Topics ادمین کنید.
3. گزینهٔ گروه و تاپیک‌ها را انتخاب و شناسهٔ `-100...` را وارد کنید.
4. پس از نمایش نام گروه و تأیید، Monitoring، Payments، Backups، System و Support
   ساخته و شناسه‌ها در دیتابیس ثبت می‌شوند.

تاپیک‌های ثبت‌شده دوباره ساخته نمی‌شوند. اگر پاسخ تلگرام هنگام ساخت قطع شود،
نصاب از مالک شناسهٔ تاپیک را می‌گیرد؛ انتخاب NEW فقط پس از بررسی ساخته‌نشدن آن
در Telegram انجام می‌شود. دفتر مراحل در `.mediahub/telegram.json` خصوصی است.
تغییر مقصدها بعداً از پنل ربات ممکن است. برای آزمایش مسیرها از Test Message پنل استفاده کنید.

رسید همچنان داخل پنل خصوصی مدیر بررسی می‌شود؛ Payments فقط گزارش تأیید را می‌گیرد.
نصاب پیام همگانی یا پیام به مشتریان نمی‌فرستد.

## عضویت و فعال‌سازی امکانات

در ادامهٔ تنظیم تلگرام، کانال عضویت و زبان `fa`، `en` یا `all` را وارد کنید.
ربات باید ادمین کانال باشد. برای کانال خصوصی لینک دعوت لازم است. افزودن دوبارهٔ
همان شناسه رکورد تکراری نمی‌سازد. فعال‌بودن شرط عضویت در پلن را هم از پنل بررسی کنید.
قیمت، کارت، کیف‌پول، پلن، مدیران، تخفیف، متن‌ها و برنامهٔ بکاپ از پنل تنظیم می‌شوند.

## آپدیت

منبع پیش‌فرض GitHub پروژه و GHCR است. سرور انتشار سفارشی باید مخزن HTTPS با تگ
نسخه و Imageهای `backend`، `bot` و `backup` با version/revision یکسان داشته باشد.
گزینهٔ سرور به‌روزرسانی این مقصدها را ذخیره می‌کند؛ تنظیم آن داخل بکاپ هم هست.
برای منابع خصوصی از credential helper و `docker login` استفاده کنید؛ توکن در URL وارد نشود.

`sudo mediahub update` آخرین تگ پایدار را برای تأیید نشان می‌دهد. نسخهٔ مشخص نیز
با `sudo mediahub update v1.0.1` انتخاب می‌شود. `latest` مبنا نیست. تغییر محلی، صف
دانلود فعال/متوقف یا آپدیت ناتمام، شروع آپدیت جدید را متوقف می‌کند.

برای نامزد آزمایشی، نسخهٔ جدید کنسول `sudo mediahub update FULL_COMMIT_SHA`
را هم می‌پذیرد. SHA باید دقیقاً ۴۰ کاراکتر، از مخزن تنظیم‌شده و ادامهٔ نسخهٔ فعلی
باشد؛ Imageها محلی ساخته می‌شوند و همان بکاپ، بررسی صف و بازگشت برقرار است.
منوی آپدیت خودکار همچنان فقط تگ‌های پایدار را انتخاب می‌کند.

Imageهای جدید ابتدا دریافت و بررسی می‌شوند. سپس پذیرش دانلود جدید متوقف و صف
دوباره بررسی می‌شود. پیش از migration بکاپ و بازیابی در دیتابیس جدا انجام می‌شود.
Imageهای واقعی قبلی حفظ می‌شوند. شکست در نسخهٔ دارای migration سازگار، برنامه را
برمی‌گرداند. migration ناسازگار، برنامه‌ها را برای بازیابی دستی متوقف نگه می‌دارد؛
دیتابیس خودکار downgrade نمی‌شود.

## بررسی یوتیوب

نسخهٔ افزونهٔ `bgutil-ytdlp-pot-provider` و سرویس Docker همراهش باید یکسان باشد.
نصاب سرویس را پیش از برنامه راه‌اندازی و سلامت اتصال از Backend را بررسی می‌کند؛
سرویس در نصب تازه، آپدیت و بازیابی برقرار می‌ماند و Image آن هم در بازگشت حفظ می‌شود.
`check_launch.sh` نتیجه را با `YOUTUBE_PROVIDER` نشان می‌دهد. این بررسی فقط `/ping`
را می‌خواند و دریافت موفق ویدئو از یوتیوب را تضمین نمی‌کند.

برای تست اطلاعات یک ویدئو با همان تنظیمات ربات و بدون دانلود فایل:

```bash
sudo bash scripts/check_youtube.sh 'https://www.youtube.com/watch?v=VIDEO_ID'
```

`YOUTUBE_EXTRACTION=LOGIN_REQUIRED` یعنی یوتیوب برای این درخواست تأیید می‌خواهد،
حتی اگر سرویس کمکی سالم باشد. تغییر لینک کوتاه به لینک کامل این محدودیت را رفع
نمی‌کند. ابتدا دسترسی همان ویدئو را بدون ورود و سپس نتیجهٔ همان تست را روی سرور
دیگر مقایسه کنید. کوکی یا حساب شخصی به‌صورت خودکار وارد نمی‌شود؛ محتوای خصوصی یا
نیازمند عضویت هم با این سرویس عمومی قابل دسترس نمی‌شود.

مراجع: [راهنمای yt-dlp](https://github.com/yt-dlp/yt-dlp/wiki/Extractors)،
[سرویس توکن](https://github.com/Brainicism/bgutil-ytdlp-pot-provider#verification).

## انتقال بکاپ به سرور تازه

بکاپ شامل دیتابیس، `.env` و `secrets` است؛ فایل رسانه و صف Redis را شامل نمی‌شود.
لینک و فعالیت کاربران در دیتابیس/بکاپ باقی می‌ماند و فقط مدیر به آن دسترسی دارد.
فایل‌های `<id>.mhb` و `<id>.json` را با هم و کلید را جداگانه نگهداری کنید.

ربات سرور قبلی را متوقف کنید. روی سرور تازه از منوی نصاب «ورود بکاپ و بازیابی»
را انتخاب و مسیر فایل و کلید مستقل را وارد کنید. checksum و رمزگشایی پیش از
استفاده از تنظیمات بررسی می‌شوند. تنظیمات پنل و رمزهای اصلی حفظ می‌شوند.
درخواست‌های قدیمی ناتمام لغو، صف پیام همگانی بازیابی‌شده متوقف و Redis خالی می‌شود.
ادامهٔ بازیابی ناتمام پس از راه‌اندازی برنامه‌ها، snapshot را دوباره روی دادهٔ تازه نمی‌نویسد.

روی نصب موجود، Restore فقط دیتابیس را برمی‌گرداند و محیط فعلی را حفظ می‌کند؛
دو تأیید، بکاپ اضطراری و نگه‌داری دیتابیس قبلی برقرار است. بکاپ نصب دیگر با کلید
متفاوت را از مسیر سرور تازه بازیابی کنید.

## گیت انتشار

CI تست‌های Backend، Bot و نصاب، PostgreSQL واقعی، ساخت Imageها و نصب هستهٔ Docker
از دیتابیس خالی و بازیابی واقعی بکاپ را اجرا می‌کند. تماس زنده با Telegram ندارد.
پیش از تگ پایدار، نصب تازه، ساخت تاپیک واقعی، Start مدیر، دانلود/خرید، انتقال بکاپ
و آپدیت/بازگشت روی محیط آزمایشی مالک باید تأیید شوند.
workflow تگ فقط پس از موفقیت CI Imageها را منتشر می‌کند. برای نصب عمومی، خواندن
هر سه Package در GHCR باید عمومی باشد و pull بدون ورود آزمایش شود؛ تگ کد به‌تنهایی
به معنی آماده‌شدن Imageها نیست.
